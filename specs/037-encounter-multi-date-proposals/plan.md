# Implementation Plan: Encounter Multi-Date Proposals & Counter-Offer Flow

**Branch**: `feat/037-encounter-multi-date-proposals` | **Date**: 2026-06-18 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `specs/037-encounter-multi-date-proposals/spec.md`

---

## Summary

Replace the current monolithic single-date encounter change flow (boolean `accepted`, full date replacement on each write, no turn tracking) with a multi-date proposal model. Either party may propose multiple candidate dates; the away team triages in a single combined action; only the home team may finalize. Per-viewer `changeStatus` is exposed as a derived GraphQL field. All existing data is migrated in a single SQL migration.

---

## Technical Context

**Language/Version**: TypeScript 5.x (Node 20 LTS)
**Primary Dependencies**: NestJS 10, `@nestjs/graphql` (code-first, Apollo), Sequelize 6 + `sequelize-typescript`, PostgreSQL 15
**Storage**: PostgreSQL — schemas `event` (models) + `public` (security/permissions). Migrations in `database/migrations/` plain JS.
**Testing**: Jest per-package, run via `turbo run test --filter=@badman/backend-graphql` and `--filter=@badman/backend-competition-change-encounter`
**Target Platform**: NestJS API (`apps/api`), Fastify adapter, port 5010
**Project Type**: Backend-only GraphQL API service
**Performance Goals**: No latency regression on the encounter list endpoint (status field resolved in-process, no extra DB round-trip per encounter)
**Constraints**: `changeStatus` MUST be resolvable without additional N+1 queries when `EncounterChange` + dates are already loaded via `@ResolveField`; the original encounter slot remains occupied (Option A) until finalization
**Scale/Scope**: Affects all active-season encounters; ~hundreds of active change requests per season

### `changeStatus` Derivation Logic

```text
Input: EncounterChange (with dates), requesting user

1. viewer_party = HOME if user.hasAnyPermission([homeTeam.clubId + '_change:encounter'])
                = AWAY otherwise

2. if no EncounterChange exists → return null

3. if any date.status === ACCEPTED → return MOVED

4. live_dates = dates where status IN (PENDING, TENTATIVELY_ACCEPTED)
   if live_dates is not empty:
     lastActionBy === viewer_party → PROPOSAL_SENT
     lastActionBy !== viewer_party → ACTION_REQUIRED

5. all dates REJECTED (no live dates):
     lastActionBy === viewer_party → ACTION_REQUIRED  (they rejected → owe new dates)
     lastActionBy !== viewer_party → REJECTED_WAITING
```

### `proposeEncounterChangeDates` Logic

```text
1. Resolve viewer party (HOME or AWAY)
2. Check change:encounter permission for viewer's club
3. Load or create EncounterChange for the encounter
4. Validate deadline: event.changeCloseRequestDatePeriodN (reject if past)
5. Validate season bounds for each incoming date (Sep 1 – Apr 30)
6. Deduplicate: reject dates already present in any non-REJECTED status
7. INSERT new EncounterChangeDate rows: status=PENDING, proposedBy=viewerParty
8. UPDATE EncounterChange: lastActionBy=viewerParty, lastActionAt=NOW()
9. Notify opposing party captain
```

### `triageEncounterChange` Logic

```text
Input: encounterChangeId, endorseIds[], rejectIds[], newDates[]

1. Resolve viewer party → must be AWAY (else PermissionDenied)
2. Load EncounterChange + all dates
3. In transaction:
   a. For each id in endorseIds: set status=TENTATIVELY_ACCEPTED (must currently be PENDING)
   b. For each id in rejectIds: set status=REJECTED (must be PENDING or TENTATIVELY_ACCEPTED)
   c. For each date in newDates: INSERT EncounterChangeDate status=PENDING, proposedBy=AWAY
   d. UPDATE EncounterChange: lastActionBy=AWAY, lastActionAt=NOW()
4. Commit
5. Notify home team captain (single notification)
```

### `finalizeEncounterChange` Logic

```text
Input: encounterChangeDateId

1. Resolve viewer party → must be HOME (else PermissionDenied)
2. Load date → must be TENTATIVELY_ACCEPTED or (proposedBy=AWAY)
   (home may only finalize endorsed dates — per FR-012)
3. Run EncounterValidationService.validate() with proposed date
   (LocationRule now activated — original slot still occupied)
4. In transaction:
   a. Set selected date status=ACCEPTED
   b. Set all PENDING/TENTATIVELY_ACCEPTED sibling dates status=RESOLVED
   c. UPDATE encounter.date = proposedDate
   d. If encounter.originalDate is null: set originalDate = current encounter.date
   e. UPDATE encounter.locationId if date carries a locationId
   f. Enqueue sync job
5. Commit
6. Notify both parties
```

### Migration Plan

Single file: `database/migrations/YYYYMMDD-add-encounter-change-multi-date.js`

```text
UP:
  1. ADD COLUMN event."EncounterChanges"."lastActionBy"  VARCHAR nullable
  2. ADD COLUMN event."EncounterChanges"."lastActionAt"  TIMESTAMPTZ nullable
  3. ADD COLUMN event."EncounterChangeDates"."proposedBy" VARCHAR nullable
  4. ADD COLUMN event."EncounterChangeDates"."status"     VARCHAR nullable
  5. BACKFILL proposedBy:
       WHERE availabilityAway IS NULL → 'HOME', else → 'AWAY'
  6. BACKFILL status:
       Find accepted EncounterChanges (accepted=true):
         date with selected=true → 'ACCEPTED'; siblings → 'RESOLVED'
       All other dates → 'PENDING'
  7. BACKFILL lastActionBy/lastActionAt:
       Per encounterChangeId: take most recent EncounterChangeDate.proposedBy/createdAt
  8. ALTER COLUMN ... SET NOT NULL  (all four new columns)
  9. DROP COLUMN event."EncounterChanges"."accepted"
  10. DROP COLUMN event."EncounterChangeDates"."selected"

DOWN:
  1. ADD COLUMN event."EncounterChanges"."accepted"        BOOLEAN DEFAULT false
  2. ADD COLUMN event."EncounterChangeDates"."selected"    BOOLEAN
  3. RESTORE accepted: WHERE any date.status='ACCEPTED' → true
  4. RESTORE selected: WHERE status='ACCEPTED' → true
  5. DROP COLUMN lastActionBy, lastActionAt, proposedBy, status
```
